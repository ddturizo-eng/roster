# Handoff — 2026-10-29

Read this first in a new session. It replaces any session memory.

## What Roster is

Async agent orchestration. A Project Manager splits goals into Linear issues, an HR Director hires
on-demand specialists, and each specialist executes and reports on its own issue. Rules live in
`AGENTS.md` and `specs/constitution.md`. Work status lives in Linear (team `ROS`).

Flow: constitution → spec (approved) → plan + ADRs → tasks → Linear issues → implementation → PR → human review.

## What spec 001 builds

A **dispatcher**: a deterministic TypeScript CLI (Node 24 type stripping, no build step, Vitest) that
runs on a GitHub Actions schedule (22:00-06:00 America/Bogota, 5 runs per night, 2 h apart). Each run:
select one ready Linear issue → hire a specialist through `hr-director` if the issue has no `agent`
label → branch `agent/ROS-<n>` → run the specialist headless through a harness adapter (Claude Code
first, subscription token) → push, open PR, comment, move issue to In Review.

Key decisions (ADRs 0006-0013 in `docs/adr/`): GitHub Actions scheduler, headless Claude Code with
subscription token, deterministic TS dispatcher, dispatcher owns all side effects (agents never push
or touch Linear in headless runs), Linear GraphQL over `fetch`, harness adapter interface, a merged
hire PR is the human approval gate for new agents, quota exhaustion pushes a WIP branch and returns
the issue to Todo.

There is no GUI. The system is built by itself: the dispatcher is the product, Linear is the UI.

## Product direction (discussed with the human, not yet a spec or ADR)

Roster is a **control plane**, not a place where apps are built. Its purpose: launch async,
specialized agents that build *other* applications. Apps never live in the Roster repo.

- Each app lives in its own GitHub repo, with its own `AGENTS.md`, `specs/`, plan and ADRs.
- Roster holds `agents/`, `skills/`, `dispatcher/` and a project registry (e.g. `projects/<app>.yml`
  with repo, stack, Linear team).
- Linear mapping: **one team per app** (own key, e.g. `SHOP-12`), **one project per feature/spec**
  inside the team. The `agent` label group is workspace-level and shared. The dispatcher is already
  configured per team (`ROSTER_TEAM_KEY`).
- Specialists are per theme (frontend, backend, db, devops) and reused across apps. Hire PRs stay in Roster.
- New app flow: human asks → empty repo created (human, or a `needs-human` issue) → spec in the app
  repo, human approves → `architect` writes plan + ADRs → `project-manager` creates issues → dispatcher
  clones the target repo, branch `agent/ROS-<n>`, PR in the app repo → human reviews and merges.
- Tracker stays Linear for now. A tracker adapter (Linear, then GitHub Issues) is deferred until
  others use Roster. Linear logic is isolated in `linear.ts` (ROS-7) so this stays possible.

Plan: finish spec 001 as-is (single repo, Roster building itself). Then write **spec 002 multi-repo**:
project registry, `prepareBranch` and push guard take a target repo, and a GitHub token that reaches
only registered repos (PAT fine-grained or GitHub App). `GITHUB_TOKEN` of the Roster workflow cannot.
This needs new ADRs that supersede parts of 0006 and 0009 (via `architect`).
Optional cheap seam for 001: T07 (ROS-9) takes the repo path as a parameter. Not applied yet.

Scope decisions (later in the same conversation, from the human):

- **No `bootstrap` command.** The human creates each app repo by hand (`gh repo create`), enables
  `main` protection (PR required, no admin bypass) and adds the repo to the token's allowed list.
  The human works on only 1-2 apps for now, so automation is not worth the risk.
- **Spec 002 stays minimal:** registry of allowed repos; `prepareBranch` and the push guard take a
  target repo; fine-grained PAT limited to registered repos; `doctor` checks `main` protection per repo.
- The dispatcher token must NOT have `Administration` (it could delete repos). Repo creation always
  uses the human's own `gh` login.
- **GUI is a later phase** (shadcn/ui + React Bits). It reads state from Linear and GitHub; no
  dispatcher redesign needed. Its own spec.

Phases: 001 single-repo dispatcher (in Linear now) → 002 minimal multi-repo → 003 possible Linear
webhooks for instant runs → 004 possible GUI. Do not define 003 and 004 until 001 and 002 work.

Status: direction agreed in conversation; the human has not approved a spec 002 yet.

## Known risks and open questions

- ROS-5 (`dispatcher-ci.yml`) and ROS-16 (`dispatcher.yml`) change `.github/workflows/`. `GITHUB_TOKEN`
  cannot push those files. Push them from an interactive session with the human's credentials.
- T06 (ROS-11) and T10 (ROS-14) may exceed 2 h. Decide whether to split them.
- Linear issue numbers start at ROS-5 because ROS-1 to ROS-4 pre-existed. Branches use `agent/ROS-<n>`.
- Specialists have no `mcp__linear` tool on purpose (ADR 0009). In interactive runs, post the closing
  comment and move the issue to In Review yourself.
- The Linear `agent` label group is workspace-level, so new child labels are created without `teamId`.
